An X.509 certificate issuance tool written in Go. It generates self-signed root certificates, intermediate certificates and domain certificates, and provides SQLite-based certificate database management (list, query, delete, revoke, unrevoke, generate CRL).

All key and certificate operations are implemented with the Go standard library, with no external commands.

## Features

- Generate root CA (`root`), intermediate CA (`inte`) and domain certificates (`cert`)
- Support ECC (prime256v1 / P-256), RSA (at least 2048 bits) and ed25519 private keys
- Save CA data to the SQLite database `xcert.db` under each CA directory
- Provide the `db` subcommand to manage the certificate database
- Revoke certificates and generate X.509 CRLs
- Customize key usage, extended key usage, CA path length, signature digest algorithm, and SKI/AKI switches
- Use random serial numbers by default, or switch to database-sequential serial numbers
- Leveled logging and colored output

## Installation

Requires Go 1.27 or later.

Build:

```sh
make build
```

Or use the Go command directly:

```sh
go build -o xcert ./cmd/xcert
```

Install to `GOPATH/bin`:

```sh
make install
```

Or install directly from the repository:

```sh
go install github.com/xireiki/xcert/cmd/xcert@latest
```

Run tests:

```sh
make test
```

Available Makefile targets: `all` (default), `build`, `race`, `test`, `vet`, `fmt`, `install`, `clean`.

## Quick start

Create a complete certificate chain (root CA, intermediate CA, domain certificate):

```sh
xcert root -D ./ca
xcert inte -D ./ca -c ./ca/RootCA.cer -k ./ca/RootCA.key
xcert cert -D ./ca -d example.com -d www.example.com
```

The output is placed in `./ca`, and the certificate database is `./ca/xcert.db`.

Inspect issued certificates:

```sh
xcert db list -D ./ca
xcert db show example.com -D ./ca
xcert info -f ./ca/certs/example.com_ecc/example.com.cer
```

Revoke a certificate and generate a CRL:

```sh
xcert db revoke example.com -D ./ca
```

## Command overview

Invocation form:

```
xcert <subcommand> [flags]
```

| Subcommand | Description |
| --- | --- |
| [`root`](#root-create-a-root-certificate) | Create a root certificate |
| [`inte`](#inte-create-an-intermediate-certificate) | Create an intermediate certificate, signed by the root certificate or a parent CA |
| [`cert`](#cert-create-a-domain-certificate) | Create a domain certificate, signed by the intermediate certificate |
| [`info`](#info-show-certificate-details) | Show details of a certificate file |
| [`db`](#db-manage-the-certificate-database) | Manage the certificate database |
| `help` | Show help information |

Running `xcert` without a subcommand prints an error and points to the help text; an unknown subcommand does the same.

`xcert help` shows the top-level help, and `xcert <subcommand> --help` shows the complete flags and defaults for that subcommand. Help output is generated by cobra from the subcommand descriptions and flag definitions.

Behavior conventions:

- Running `root`, `inte` or `cert` with no arguments prints that subcommand's help instead of performing an operation. As soon as any argument (including any flag) is given, it runs with those arguments.
- Running `info` without `-f` / `--file` reports an error.
- Running `db` with no arguments prints its help; its subcommands that require arguments (such as `show`, `delete`, `revoke`) report an error when arguments are missing.

## Global options and behavior

### Global flags

| Flag | Default | Description |
| --- | --- | --- |
| `--log-level` | `info` | Log level; one of `trace`, `debug`, `info`, `warn`, `error`, `fatal`, `panic`, and `warning` is also accepted |
| `--legacy` | `false` | Read a legacy `xcert.sh` directory (`serial`, `index.txt`); see [Legacy xcert.sh directory](#legacy-xcertsh-directory) |

These flags may be placed before or after any subcommand.

### Subject format

`-s` / `--subject` takes a slash-separated subject string such as `/C=CN/O=Test SSL/CN=Test SSL CA`. Supported field keys (case-insensitive):

| Key | Meaning |
| --- | --- |
| `C` | Country |
| `ST` or `S` | State or Province |
| `L` | Locality |
| `O` | Organization |
| `OU` | Organizational Unit |
| `CN` | Common Name |
| `emailAddress` or `E` | Email address |

`C`, `ST`, `L`, `O` and `OU` may repeat and accumulate into multiple values; `CN` overwrites the previous value on each occurrence; `emailAddress` may repeat and accumulate. Empty fields are ignored; a segment without `=` reports an error instead of being silently dropped.

### Logging

Log levels, from low to high, are `panic`, `fatal`, `error`, `warn`, `info`, `debug`, `trace`. The default level is `info`, meaning only messages at `info` or above are printed; a higher level (such as `debug` or `trace`) prints more detail, while a lower level (such as `error`) suppresses `info` and `warn`.

All logs go to standard error. Tags are always the uppercase English level name:

| Level | Tag |
| --- | --- |
| `panic` | `PANIC` |
| `fatal` | `FATAL` |
| `error` | `ERROR` |
| `warn` | `WARN` |
| `info` | `INFO` |
| `debug` | `DEBUG` |
| `trace` | `TRACE` |

When standard error is a terminal and the `NO_COLOR` environment variable is not set, tags are colored: `ERROR`, `FATAL` and `PANIC` are red, `WARN` is yellow, `INFO` is cyan, and `DEBUG` and `TRACE` are white. Otherwise the output is plain text.

Command data (such as the output of `db list` and `db show`) goes to standard output, separated from logs so it can be redirected.

### Exit codes

- `0`: success
- `1`: argument errors, missing files, processing failures other than an already existing certificate

## root: create a root certificate

### Flags

| Flag | Default | Description |
| --- | --- | --- |
| `-C`, `--cipher` | `ecc` | Private key type; one of `ecc`, `rsa` or `ed25519`. Any other value reports an error |
| `--rsa-bits` | `3072` | RSA key length in bits; only takes effect with `--cipher rsa`, minimum 2048 |
| `-s`, `--subject` | `/C=CN/O=Test SSL/CN=Test SSL CA` | Certificate subject |
| `--days` | `3650` | Certificate validity in days; must be positive |
| `-D`, `--dir` | `.` | Output directory |
| `--key-usage` | `keyCertSign,cRLSign` | Key usage extension, comma-separated; multiple values are combined |
| `--ext-key-usage` | empty | Extended key usage, comma-separated |
| `--path-length` | `-1` | CA path length constraint; `-1` leaves it unset |
| `--digest` | `sha512` | Signature digest algorithm; one of `sha256`, `sha384`, `sha512` |
| `--subject-key-id` | `true` | Include the Subject Key Identifier (SKI) |
| `--authority-key-id` | `true` | Include the Authority Key Identifier (AKI). A root certificate is self-signed and never carries an AKI by default, so this flag has no practical effect on root certificates |
| `-h`, `--help` | | Show help |

See [Shared flags reference](#shared-flags-reference) for the values and semantics of `--key-usage`, `--ext-key-usage`, `--path-length`, `--digest`, `--subject-key-id` and `--authority-key-id`.

### Behavior

- If `RootCA.cer` already exists in the target directory, a warning is printed and the command returns without overwriting it.
- Creates the directory and `<dir>/newcerts`, `<dir>/crl`.
- If `<dir>/RootCA.key` does not exist, generates a private key according to `--cipher`.
- Generates the self-signed root certificate `RootCA.cer`; the signature digest algorithm is chosen by `--digest`.
- Records the root certificate in `<dir>/xcert.db` with type `root` and name `RootCA`.
- Root certificates always use a random serial number (128 bits).

The root certificate contains `keyUsage` (`keyCertSign,cRLSign`) and `basicConstraints` (`CA:TRUE`) by default, and includes an SKI by default.

### Output files

| File | Description |
| --- | --- |
| `RootCA.key` | Private key, mode 0600 |
| `RootCA.cer` | Self-signed root certificate |
| `xcert.db` | Certificate database |
| `newcerts/` | Reserved directory |
| `crl/` | CRL output directory |

## inte: create an intermediate certificate

### Flags

| Flag | Default | Description |
| --- | --- | --- |
| `-C`, `--cipher` | `ecc` | Private key type; one of `ecc`, `rsa` or `ed25519` |
| `--rsa-bits` | `3072` | RSA key length in bits, minimum 2048 |
| `-s`, `--subject` | `/C=CN/O=Test SSL/CN=Test Inte CA` | Certificate subject |
| `--days` | `1825` | Certificate validity in days; must be positive |
| `-D`, `--dir` | `.` | Output directory |
| `-c`, `--cert` | none, required | Path to the parent CA certificate that signs the intermediate certificate |
| `-k`, `--key` | none, required | Path to the parent CA private key that signs the intermediate certificate |
| `--sequential-serial` | `false` | Use the database sequential counter as the serial number; random by default |
| `--key-usage` | `keyCertSign,cRLSign` | Key usage extension |
| `--ext-key-usage` | empty | Extended key usage |
| `--path-length` | `0` | CA path length constraint; `-1` leaves it unset |
| `--digest` | `sha512` | Signature digest algorithm |
| `--subject-key-id` | `true` | Include the SKI |
| `--authority-key-id` | `true` | Include the AKI |
| `-h`, `--help` | | Show help |

See [Shared flags reference](#shared-flags-reference) for the values and semantics of `--key-usage`, `--ext-key-usage`, `--path-length`, `--digest`, `--subject-key-id` and `--authority-key-id`.

### Behavior

- If `InteCA.cer` already exists in the target directory, a warning is printed and the command returns without overwriting it.
- `-c` and `-k` are required; a missing flag or a nonexistent file reports an error.
- The parent CA certificate must be a CA certificate permitted to sign certificates, otherwise an error is reported.
- Creates the directory and `<dir>/newcerts`, `<dir>/crl`, `<dir>/certs`.
- If `<dir>/InteCA.key` does not exist, generates a private key according to `--cipher`.
- Generates the certificate request `InteCA.csr` (if absent).
- Signs `InteCA.cer` with the parent CA certificate and private key.
- Generates the certificate chain `chain.cer`, containing `InteCA.cer` concatenated with the parent CA certificate.
- Records the intermediate certificate in the database with type `inte` and name `InteCA`.
- The certificate `NotAfter` is the earlier of the requested number of days and the parent CA's `NotAfter`, so it never outlives the issuer.
- If the parent CA has no SKI, no AKI is attached.

Random serial numbers are used by default; with `--sequential-serial`, the value is read from and incremented in the database counter instead.

### Output files

| File | Description |
| --- | --- |
| `InteCA.key` | Private key, mode 0600 |
| `InteCA.csr` | Certificate request |
| `InteCA.cer` | Intermediate certificate |
| `chain.cer` | Certificate chain: intermediate certificate concatenated with the parent CA certificate |
| `xcert.db` | Certificate database |
| `certs/` | Domain certificate directory |
| `newcerts/`, `crl/` | Reserved directories |

## cert: create a domain certificate

### Flags

| Flag | Default | Description |
| --- | --- | --- |
| `-C`, `--cipher` | `ecc` | Private key type; one of `ecc`, `rsa` or `ed25519` |
| `--rsa-bits` | `3072` | RSA key length in bits, minimum 2048 |
| `-s`, `--subject` | `/C=CN` | Certificate subject |
| `--days` | `90` | Certificate validity in days; must be positive. With `--code-signing` and no explicit value, defaults to `365` |
| `-D`, `--dir` | `.` | CA directory, used to locate the database, CA certificate, CA private key and certificate chain |
| `-c`, `--cert` | `<dir>/InteCA.cer` | CA certificate used to sign the certificate |
| `-k`, `--key` | `<dir>/InteCA.key` | CA private key used to sign the certificate |
| `--chain` | `<dir>/chain.cer` | Certificate chain concatenated into `fullchain.cer` (regular certificates) or the `.pfx` (code signing certificates) |
| `--ext-key-usage` | `serverAuth,clientAuth` | Extended key usage, comma-separated; when empty the extension is not written |
| `--code-signing` | `false` | Issue a Windows code signing certificate; the extended key usage is fixed to `codeSigning` and this flag is mutually exclusive with `--ext-key-usage` |
| `--pfx-password` | empty | Password for the generated `.pfx` file; only used with `--code-signing` |
| `-d`, `--domain` | none | Domain name; may be repeated |
| `--csr` | none | Sign an external certificate request, using the request's public key and subject, without generating a key or request |
| `--sequential-serial` | `false` | Use the database sequential counter as the serial number; random by default |
| `-h`, `--help` | | Show help |

See [Shared flags reference](#shared-flags-reference) for the values and semantics of `--ext-key-usage`.

### Common name and SAN rules

- The common name `CN` and `subjectAltName` are always written, satisfying RFC 6125 hostname verification.
- If at least one domain is given via `-d`, the subject `CN` is the first domain (overriding the `CN` from `--subject` or the certificate request), and `subjectAltName` contains all domains.
- If `-d` is not given, the `CN` from `--subject` is used as the domain and written to `subjectAltName`.
- If both the `-d` domains and the `--subject` `CN` are empty, an error is reported.
- The common name is checked for path safety: it is rejected when empty, equal to `.` or `..`, or containing a path separator or control character, preventing the output path from escaping the CA directory.

### Behavior

- Computes the common name `CN` and determines the output directory `<dir>/certs/<CN>_<cipher>`.
- If the target artifact already exists (`fullchain.cer` for regular certificates, `<CN>.pfx` for code signing certificates), a warning is printed and the command returns.
- If `<CN>.key` does not exist, generates a private key according to `--cipher`; an existing key whose type does not match `--cipher` reports an error.
- If `<CN>.csr` does not exist, generates a certificate request containing the same `subjectAltName` as the certificate; an existing request that does not match the current subject or `subjectAltName` is regenerated.
- Signs `<CN>.cer` with the CA certificate and private key.
- The CA certificate used for signing must be a CA certificate permitted to sign certificates, otherwise an error is reported.
- Regular certificates get a full chain `fullchain.cer` for `<CN>`, containing `<CN>.cer` concatenated with the contents of the file given by `--chain`; if `<CN>.cer` already exists but `fullchain.cer` is missing, it is rebuilt. Code signing certificates produce `<CN>.pfx` instead (see below).
- Records the domain certificate in the database with type `cert` and name `CN`.
- The certificate `NotAfter` is the earlier of the requested number of days and the signing CA's `NotAfter`, so it never outlives the issuer.
- If the signing CA has no SKI, no AKI is attached.

Key usage is determined automatically from the key type: ECDSA and ed25519 keys use `digitalSignature`; RSA keys use `digitalSignature,keyEncipherment`. Extended key usage is controlled by `--ext-key-usage`, defaulting to `serverAuth,clientAuth`, and `basicConstraints` is `CA:FALSE`. The signature digest algorithm is fixed to SHA-256.

### Code signing certificates

`cert --code-signing` issues a leaf certificate for signing Windows programs:

- Extended key usage is fixed to `codeSigning` (1.3.6.1.5.5.7.3.3), and key usage is fixed to `digitalSignature`.
- The default validity becomes 365 days; an explicit `--days` takes precedence.
- Mutually exclusive with `--ext-key-usage`; specifying both reports an error. It cannot be combined with `--csr` either.
- Only used to issue leaf certificates; before signing, the signing CA's extended key usage is checked: allowed only when the CA has no EKU or includes `codeSigning` / `any`, otherwise an error is reported.
- Does not generate `fullchain.cer`; instead generates a PKCS#12 file `<CN>.pfx` containing the leaf certificate, its private key and the CA chain from `--chain`, protected by the password given to `--pfx-password` (empty by default). The PFX is encrypted with PBES2 + PBKDF2-HMAC-SHA-256 + AES-256-CBC.

### Signing external certificate requests

`--csr` signs a certificate request supplied by someone else. The flow is:

- Parse the request file and verify its signature; an invalid signature or malformed file reports an error.
- Use the public key and subject from the request, and do not generate a local private key; `--cipher`, `--rsa-bits` and `--subject` have no effect in this mode.
- `subjectAltName` is the union of the domains in the request and those given by `-d`, with `-d` domains first; `CN` is the first domain of the union.
- The common name is the first domain of the union; if neither the request nor `-d` has a domain, the request subject's `CN` is used.
- The output directory matches local generation: `<dir>/certs/<CN>_<key type>`, where the key type is derived from the request's public key (`ecc`, `rsa`, `ed25519`).
- In this mode only `<CN>.cer`, a copy of the external request `<CN>.csr` and `fullchain.cer` are written; no `<CN>.key` is written, and `key_path` in the database record is empty.

### Output files

Under `<dir>/certs/<CN>_<cipher>/`:

| File | Description |
| --- | --- |
| `<CN>.key` | Private key, mode 0600; not generated with `--csr` |
| `<CN>.csr` | Certificate request containing the same `subjectAltName` as the certificate; with `--csr`, a copy of the external request |
| `<CN>.cer` | Domain certificate |
| `fullchain.cer` | Full chain of the domain certificate concatenated with the certificate chain; not generated with `--code-signing` |
| `<CN>.pfx` | PKCS#12 file of a code signing certificate (only `--code-signing`), containing the leaf certificate, private key and CA chain, replacing `fullchain.cer` |

## db: manage the certificate database

The database file is always `xcert.db` under the CA directory, specified with the persistent flag `-D` / `--dir` (default `.`). The flag may be placed before or after the subcommand.

### Subcommands

| Subcommand | Description |
| --- | --- |
| `db list` | List all records in the database |
| `db show <serial\|name>` | Show one record by serial number or name |
| `db import <cert-file>` | Import an existing certificate file into the database |
| `db delete <serial\|name>` | Delete a record; revoked records require `--force`, and a tombstone is kept |
| `db revoke <serial\|name>` | Mark a record as revoked and regenerate the CRL |
| `db unrevoke <serial\|name>` | Restore a record to valid and regenerate the CRL |

`<serial|name>` accepts a hexadecimal serial number (case-insensitive) or a certificate name. If a name matches multiple records, the result is reported as ambiguous and a serial number is required.

### db list output

Prints a table in insertion order with the following columns:

| Column | Description |
| --- | --- |
| `SERIAL` | Serial number (hexadecimal, uppercase) |
| `TYPE` | Type: `root`, `inte`, `cert` |
| `NAME` | Name: `RootCA`, `InteCA` or a domain |
| `STATUS` | Status: `V` valid, `R` revoked |
| `NOT_AFTER` | Expiry time, RFC 3339 format |

### db show output

Prints all fields of a single record:

| Field | Description |
| --- | --- |
| `Serial` | Serial number |
| `Type` | Type |
| `Name` | Name |
| `Subject` | Subject |
| `Status` | Status |
| `NotBefore` | Valid-from time |
| `NotAfter` | Expiry time |
| `Cert` | Certificate file path |
| `Key` | Private key file path |
| `Created` | Record creation time |
| `Revoked` | Revocation time, empty when not revoked |

### db import flags

Imports an existing certificate file into the database. This is useful for restoring records after `xcert.db` is lost or corrupted, or for importing externally generated certificates.

| Flag | Default | Description |
| --- | --- | --- |
| `--key` | empty | Private key path stored in the record; normalized to an absolute path |
| `--name` | the certificate `CN` | Record name |

`db import <cert-file>` reads the serial number, subject, `NotBefore` and `NotAfter` from the certificate and writes them to the database; certificate and private key paths are stored as absolute paths. The record type is derived from the certificate itself: non-CA is `cert`, self-signed CA is `root`, and the rest is `inte`; it cannot be overridden manually. If a record for that serial number already exists, a warning is printed and the import is skipped. Before importing, the certificate signature is verified: a self-signed certificate must be validly self-signed (and be a CA), and any other certificate must verify against a signing CA already present among the database's `root`/`inte` records, otherwise an error is reported. Import order should therefore be root certificate, intermediate certificate, then leaf certificate. Relative `cert_path` values saved by earlier versions are still resolved against the current working directory; after moving an old database, re-importing the issuer CA by absolute path may be needed to restore signature verification.

### db delete flags

In addition to `-D` / `--dir`, it supports:

| Flag | Default | Description |
| --- | --- | --- |
| `--force` | `false` | Delete a revoked record; a tombstone record is kept so the serial number remains on the CRL |

`db delete` removes the database record; for domain certificates (`cert`) it also deletes the corresponding `<CN>.cer`, `<CN>.key`, `<CN>.csr`, `<CN>.pfx` and `fullchain.cer`. Whether files are deleted depends on the certificate itself: if it loads as a CA certificate, no file is deleted and only the database row is removed, so `root` and `inte` records never lose their CA files; if `<CN>.cer` is already missing and the type cannot be determined, the command falls back to the recorded type, and `cert` records still have their private key and other files cleaned up. Records already revoked (`R`) are refused by default and require `--force`; with `--force` the record is soft-deleted, no longer shown by `db list`, but its serial number remains on the CRL.

### revoke / unrevoke flags

In addition to `-D` / `--dir`, they support:

| Flag | Default | Description |
| --- | --- | --- |
| `--ca-cert` | `<dir>/InteCA.cer` | CA certificate used to sign the CRL |
| `--ca-key` | `<dir>/InteCA.key` | CA private key used to sign the CRL |
| `--crl` | `<dir>/crl/<CA file name>.crl` | CRL output path |
| `--digest` | `sha512` | CRL signature digest algorithm; one of `sha256`, `sha384`, `sha512` |
| `--crl-days` | `30` | Number of days from now for the CRL `nextUpdate`; must be positive |

`revoke` first sets the matching record's status to `R` and records the revocation time, then regenerates the CRL; `unrevoke` first restores the status to `V` and clears the revocation time, then regenerates the CRL. If CRL generation fails, the command reports an error and rolls back the status change, keeping the database and CRL consistent. The CA certificate used to sign the CRL must be a CA certificate permitted to sign CRLs, and its private key must match the certificate. `root` and `inte` records cannot be revoked or unrevoked: CRLs only include domain certificates, and revoking a CA record reports an error.

The CRL uses the `X509 CRL` PEM format. The CRL number comes from a separate incrementing counter in the database `meta` table and is allocated before signing. The CRL contains every domain certificate record with status `R`, including soft-deleted tombstone records.

## Shared flags reference

`--key-usage`, `--path-length`, `--digest`, `--subject-key-id` and `--authority-key-id` are supported only by `root` and `inte`; `--ext-key-usage` is supported by `root`, `inte` and `cert`.

### --key-usage

A comma-separated list of key usage names; multiple values are combined. Accepted values:

| Value | Meaning |
| --- | --- |
| `digitalSignature` | Digital signature |
| `nonRepudiation` / `contentCommitment` | Non-repudiation / content commitment |
| `keyEncipherment` | Key encipherment |
| `dataEncipherment` | Data encipherment |
| `keyAgreement` | Key agreement |
| `keyCertSign` | Certificate signing |
| `cRLSign` / `crlSign` | CRL signing |
| `encipherOnly` | Encipher only |
| `decipherOnly` | Decipher only |

An unrecognized value reports an error.

### --ext-key-usage

A comma-separated list of extended key usage names. Accepted values:

| Value | Meaning |
| --- | --- |
| `serverAuth` | TLS server authentication |
| `clientAuth` | TLS client authentication |
| `codeSigning` | Code signing |
| `emailProtection` | Email protection |
| `ipsecEndSystem` | IPsec end system |
| `ipsecTunnel` | IPsec tunnel |
| `ipsecUser` | IPsec user |
| `timeStamping` | Time stamping |
| `ocspSigning` / `OCSPSigning` | OCSP signing |
| `any` / `anyExtendedKeyUsage` | Any purpose |

An unrecognized value reports an error.

The default for `cert` is `serverAuth,clientAuth`; an empty value (such as `--ext-key-usage=`) leaves the extension unwritten.

### --path-length

CA path length constraint. The value `-1` leaves the constraint unset; `0` allows only end-entity certificates and no further subordinate CAs; a value greater than `0` allows that many levels of subordinate CAs.

### --digest

Signature digest algorithm; one of `sha256`, `sha384`, `sha512`. The matching algorithm is chosen automatically from the key type (RSA uses RSASSA-PKCS1-v1_5, ECC uses ECDSA); ed25519 ignores this flag and always uses Ed25519.

### --subject-key-id and --authority-key-id

These control whether the SKI and AKI extensions are included.

- With `--subject-key-id=true` (default), the SKI is generated by the standard library per RFC 7093 method 1 (SHA-256 of `subjectPublicKey`, truncated to 160 bits).
- With `--subject-key-id=false`, the tool manually encodes the `basicConstraints` extension and makes the standard library skip automatic SKI generation by not treating the certificate as a CA. The resulting certificate still carries the correct `CA:TRUE` extension and chains verify normally.
- With `--authority-key-id=true` (default), the AKI is derived by the standard library from the parent certificate's SKI.
- With `--authority-key-id=false`, the tool clears the SKI from the parent certificate object before signing, so the standard library cannot derive an AKI.

## Reference

### Keys and file formats

- ECC private key: secp256r1 (prime256v1 / P-256), PEM type `EC PRIVATE KEY`
- ed25519 private key: PEM type `PRIVATE KEY` (PKCS#8)
- RSA private key: PEM type `RSA PRIVATE KEY` (PKCS#1)
- Certificate: PEM type `CERTIFICATE`
- Certificate request: PEM type `CERTIFICATE REQUEST`
- CRL: PEM type `X509 CRL`
- Private key files use mode `0600`; all other files use mode `0644`

### Directory layout example

After running `xcert root -D ./ca`, `xcert inte -D ./ca -c ./ca/RootCA.cer -k ./ca/RootCA.key` and `xcert cert -D ./ca -d example.com -d www.example.com`, the directory layout is:

```
ca
├── RootCA.key                root CA private key
├── RootCA.cer                root CA self-signed certificate
├── InteCA.key                intermediate CA private key
├── InteCA.csr                intermediate CA certificate request
├── InteCA.cer                intermediate CA certificate
├── chain.cer                 certificate chain: intermediate CA concatenated with the parent CA
├── xcert.db                  certificate database (SQLite)
├── certs
│   └── example.com_ecc       domain certificate directory, named <CN>_<key type>
│       ├── example.com.key   domain private key
│       ├── example.com.csr   domain certificate request
│       ├── example.com.cer   domain certificate

    └── InteCA.crl            CRL signed by the intermediate CA
```

### Database schema

`xcert.db` is a SQLite database with the following tables.

`meta` table:

| Column | Type | Description |
| --- | --- | --- |
| `key` | TEXT | Primary key, counter name: `serial` or `crl` |
| `value` | TEXT | Current counter value, hexadecimal |

`certs` table:

| Column | Type | Description |
| --- | --- | --- |
| `id` | INTEGER | Primary key, auto-increment |
| `serial` | TEXT | Serial number, uppercase hexadecimal |
| `subject` | TEXT | Subject |
| `type` | TEXT | Type: `root`, `inte`, `cert` |
| `name` | TEXT | Name |
| `status` | TEXT | Status: `V` or `R` |
| `not_before` | TEXT | Valid-from time, RFC 3339 |
| `not_after` | TEXT | Expiry time, RFC 3339 |
| `cert_path` | TEXT | Certificate path |
| `key_path` | TEXT | Private key path |
| `created_at` | TEXT | Record creation time, RFC 3339 |
| `revoked_at` | TEXT | Revocation time, RFC 3339, empty when not revoked |
| `deleted` | INTEGER | Whether soft-deleted; `1` marks a tombstone record hidden from `db list`/`db show` but still included in the CRL |

Serial numbers use a random 128-bit value by default and do not consume the database counter; with `--sequential-serial`, the `serial` counter (initially `01`) is read and incremented. `root` always uses a random serial number. CRL numbers use the separate `crl` counter.

### Legacy xcert.sh directory

With the global flag `--legacy` and `-D` pointing at a CA directory produced by the old [`xcert.sh`](https://gist.github.com/xireiki/acb4b35c49538ccfdb98c014747edc74), the tool reads the legacy file structure and records so new certificates can continue to be issued:

- Private keys: supports legacy OpenSSL `EC PARAMETERS` + `EC PRIVATE KEY` files, as well as RSA private keys.
- Records: if `serial` or `index.txt` exists in the directory, the first open reads `serial` to continue the `--sequential-serial` counter, and imports issued/revoked records from `index.txt` into `xcert.db`.
- This directory structure is deprecated and produces a `WARN`-level deprecation warning when read.

#### How to import (xcert.sh)

The import happens automatically the first time the database is opened; there is no separate command. Run any command in the legacy directory with `--legacy`, for example:

```sh
xcert --legacy db list -D ./oldca
```

The first run creates `xcert.db` under `./oldca`, writes `serial` into the `meta.serial` counter, imports the records from `index.txt` into the `certs` table, and prints a `WARN`-level deprecation warning. Once imported, the records live in `xcert.db`, so later commands can drop `--legacy`:

```sh
xcert db list -D ./oldca
```

The import happens only once (when the `certs` table is empty), and the tool never writes back to `serial` or `index.txt`; new records are still written only to `xcert.db`. Without `--legacy`, `serial` and `index.txt` are ignored. The import has two known downgrades: `index.txt` cannot distinguish categories, so all records are imported as type `cert`; and records carry no original valid-from time, so `not_before` is set to the import time. If this is a problem, use `db import` to re-import specific certificates.

### Standards compliance

Certificate generation is designed around the following specifications:

- RFC 5280: certificate validity never exceeds the issuer; `keyUsage` and `basicConstraints` extensions; Authority Key Identifier (AKI) computation.
- RFC 6125: hostnames are always expressed through `subjectAltName`, with `CN` and `subjectAltName` kept consistent.
- RFC 5480: ECDSA certificates omit `keyEncipherment` from `keyUsage`.
- CA/Browser Forum Baseline Requirements: server certificate signatures use SHA-256; CA certificates include `keyCertSign`; RSA key length is at least 2048; serial numbers contain at least 64 bits of cryptographic randomness.
- Generated certificates set `NotBefore` one minute before the current time to avoid clients treating them as not yet valid due to clock skew.

## AI development guidelines

This repository allows AI assistants to participate in development. Changes produced by AI follow the same standards as human changes and are merged only after maintainer review; behavior constraints for AI assistants live in `AGENTS.md`, and this section only describes the requirements for AI-related contributions from the project's point of view.

### Commits and testing

- Before committing, run `go vet ./...` and `go test ./...`, and actually exercise the relevant commands to self-test; confirm everything passes.
- Keep `README.md` in sync with every commit, so the subcommands, flags, defaults, file layout and behavior it documents match the code.
- Use Conventional Commits for commit messages: `<type>(<scope>): <description>`.

### Code change principles

- Make the smallest change that completes the task; do not refactor unrelated code along the way.
- Changes must not degrade performance or break existing functionality.
- Prefer the standard library and existing dependencies; do not add a dependency for a problem a few lines of code can solve.
- Do not add unrequested abstractions, configuration options, or scaffolding for "maybe later".
- Leave one runnable check (a test or self-check) for any non-trivial logic.

### Flags and directory conventions

- Command-line flags consistently use GNU kebab-case long options.
- The CA directory flag is always `-D` / `--dir`.
- Long options use hyphens, such as `--rsa-bits`, `--path-length`, `--digest`, `--sequential-serial`, `--crl-days`.
- Keep short options for frequent operations; everything else is long-only.
- Directory responsibilities: `cmd/xcert/` is the command-line entry point (one `cmd_*.go` per subcommand); `pki/` holds key and certificate operations; `store/` holds the SQLite database; `option/` holds flag structs; `log/` holds log levels and output.
- Command help is generated by cobra from `Short` and flag descriptions; never hardcode help text in code.
